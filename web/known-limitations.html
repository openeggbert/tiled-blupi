Known Limitations

tiled-blupi provides solid read/write support for Speedy Blupi level files, but several aspects of the BLP format are unknown or not fully implemented. This page documents every known limitation so you can work around them.

Unknown Header Region (0x40–0x363)

Highest-risk limitation
The 804 bytes between the end of the name field and the start of the foreground tile layer are of unknown structure. The extension writes zeros here on every save.

If the original level file had non-zero data in this region, saving with tiled-blupi will destroy that data. Some levels may store configuration, scripting hints, or other data here that the game requires. This is the most likely cause of game crashes after editing.

Workaround: If a level crashes after editing, consider using a hex editor to copy the original 0x40–0x363 bytes from the backup into the saved file.

Unknown Trailing Data

Approximately 512 bytes at the end of the file (from offset 0xC324) are also of unknown structure and are written as zeros. The impact is less certain than the header issue.

Background Image Updates Require Level Reopen

Changing the background map property in Tiled does not immediately update the displayed background image layer. You must close and reopen the level file in Tiled to see the new background. The new value is written correctly to the BLP file on save.

No Write-Time Validation

The extension does not validate data before writing:

  • Tile IDs beyond the tileset size are written without error and may crash the game.
  • Object count exceeding 200 results in silent truncation with no warning.
  • Invalid property values (e.g., negative tile coordinates) are not checked.

Object Struct Fields 0x04–0x09 Zeroed

6 bytes at the start of each object struct (+0x04 to +0x09) are of unknown purpose and are zeroed on write. If the original level had non-zero values here, they are lost on save.

Unknown Object Fields: Preserved But Purpose Unknown

Several object fields are preserved verbatim on round-trip but their purpose is not documented: field_A, field_24, field_26, field_28, field_2E. These values are displayed in the Tiled Properties panel but you cannot know what changing them does without game testing.

tileset_id and tile_id Not Reconstructed

The game uses tileset_id and tile_id in the object struct to select the sprite for rendering. These values are preserved from the original file but are not reconstructed by the extension when you add a new object. New objects added in Tiled may have incorrect or zero values for these fields, potentially causing the game to display the wrong sprite or no sprite for the object.

Workaround: After adding new objects, compare their tileset_id and tile_id values with similar objects from the original retail levels and set them manually in Tiled.

Maximum 200 Objects Per Level

The BLP format supports exactly 200 object slots. Adding more than 200 objects in Tiled will silently drop all objects beyond the 200th when saving.

No Support for Creating Levels from Scratch

The extension does not support creating a new, blank level file via Tiled's "New Map" dialog. To create a custom level, start by copying and renaming an existing retail level file.

element and blupi Tilesets Not Used

The element and blupi000–blupi003 tilesets are included in the repository and project but are not used by sblv.js for any layer. Their purpose in the workflow is not documented.

SB1/SB2 Extensions Are Not Shared

Changes to SB1's sblv.js are not automatically applied to SB2's version and vice versa. They are maintained as separate copies. Improvements to one may not be reflected in the other.

No License File in the Repository

As of the time this documentation was written, the repository does not contain a license file. The legal status of tiled-blupi (including the extracted PNG tile images) is therefore unclear. See License for more information.
